# 标定指南

把本包中每一个占位值替换为实测值的完整流程 —— 从物理夹爪、Python SDK，
一直写到 URDF/xacro 参数。

[English](calibration-guide.md) · **简体中文**

> **请先读这一段。** SDK 的标定例程**并不测量**夹爪行程。它测的是电机的*角度*范围，
> 然后用 **「假定行程 ÷ 实测角度范围」** 推算出 mm 刻度。出厂设定假定行程为
> **120 mm**，而本夹爪的真实机械行程是 **87 mm**。在修正这一点之前，
> SDK 报告的每一个毫米读数都**偏大 1.38 倍**。
> 第 2 步的存在就只为了修掉这个问题，它不是可选项。

---

## 标定对象一览

| 标定量 | 影响 | 方法 | 工具 | 写入位置 |
| --- | --- | --- | --- | --- |
| 机械行程 | 下游全部 | 直接测量 | 数显卡尺 | `GripperConfig.max_stroke_mm`、URDF `stroke` |
| 两端极限的角度范围 | mm 刻度 | SDK 驱动顶到两端硬限位 | — | 标定 JSON 的 `travel_range_rad` |
| `rad_to_mm` | 所有 mm 读数 | 计算：`行程 / 角度范围` | — | 标定 JSON 的 `rad_to_mm` |
| 位置精度 | 抓取可靠性 | 下发并实测 | 数显卡尺 | 验收记录 |
| N/Nm（每牛米多少牛） | 夹持力精度 | 两指之间放测力计 | 测力计 | `UnitConversion.NM_TO_N` / `N_TO_NM` |
| 最大夹持力 | URDF `effort` | 测力计，逐步加力矩 | 测力计 | URDF `effort` |
| 单指最大速度 | URDF `velocity` | 计时走过已知距离 | 卡尺 + 秒表 | URDF `velocity` |
| 关节摩擦 | URDF `joint_friction`（**仅仿真**） | 电机失能后拉扯测突破力 | 测力计 | URDF `joint_friction` |
| 关节阻尼 | URDF `joint_damping`（**仅仿真**） | 测力 vs 速度扫描 | 测力计 | URDF `joint_damping` |

`effort` 与 `velocity` 是对真机生效的约束。`joint_damping` 与 `joint_friction`
只有物理仿真器会读 —— ros2_control 硬件接口会忽略它们。
在其余项目完成之前，不要把测力计的时间花在阻尼和摩擦上。

## 坐标系统 —— 动手前必读

同一物理开口有三套不同的位置表示，它们的零点和方向都不一致。
把它们混为一谈，是产生错误数字最可能的方式。

| 表示方式 | 完全闭合 | 完全张开 | 方向 |
| --- | --- | --- | --- |
| **电机位置**（rad） | ≈ `+0.114` | ≈ `-1.491` | 夹爪张开时**减小** |
| **SDK 位置**（mm） | `0` | `max_stroke_mm`（= 87） | 夹爪张开时增大 |
| **URDF 关节** `q`（m） | `0.0435` | `0.0` | 夹爪张开时**减小** |

上表中的 rad 值来自随包出厂的标定文件，必须在第 3 步重新测量。

**换算关系。** 记 `p` 为 SDK 位置（mm），`q` 为 URDF 关节值（m），
`r` 为电机位置（rad），`r_closed` 为闭合限位的 rad 值，`k` = `rad_to_mm`。

```text
p = (r_closed - r) * k                    r = r_closed - p / k
q = 0.0435 * (1 - p / 87.0)               p = 87.0 * (1 - q / 0.0435)
```

用几何关系校验这组桥接公式：`p = 0`（闭合）给出 `q = 0.0435` ✓；
`p = 87`（张开）给出 `q = 0` ✓。

## 前置条件

**供电与接线。** 电机需要 **24 V** 才能输出力矩。CAN 由 USB-CAN 适配器单独供电，
因此不接 24 V 时夹爪仍能在总线上应答 —— 但它会上报 `UV_FAULT` 并拒绝运动。
若标定看起来卡住、位置读数始终不变，先查 24 V，再查别的。

**拉起 CAN。** 经典 CAN，1 Mbps：

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000 fd off
sudo ip link set can0 up
ip -details link show can0        # 确认 state UP 且 bitrate 1000000
```

**安装 SDK。**

```bash
cd /path/to/lite-grip
pip install -e .
```

**标定前先确认通信。** 绝不要在未经确认的总线上开始标定：

```bash
python examples/can_diag.py --channel can0 --can-id 0x08
```

应能看到合法的状态帧与合理的位置值。若此步失败，先停下来修链路 ——
标定会把夹爪顶进硬限位，那不是发现连接不稳的地方。

**清空工作区。** 第 3、4 步中夹爪会自行顶到两端机械限位。
请可靠地固定它，或握稳它，确保两指之间没有东西、两指的行程路径上也没有东西。
手指远离。

## 第 1 步 —— 测量真实行程

行程是 SDK 唯一无法自行获知的量。直接测。

1. **卸掉驱动力。** 进入零重力模式让两指可自由移动：`gripper.enter_zero_gravity()`，
   或以 `manual` 模式运行标定脚本（见第 3 步方案 B）。
   若机构不自锁，断电也可以。
2. **用手把两指完全推拢**，抵住闭合硬限位。
3. **用数显卡尺在两指指尖处的内侧面之间测量。** 这是零点参考，
   记为 `O_closed`。对建模正确的夹爪，该读数应为 **0.00 mm**。
   若非零，说明两指未完全贴合，或硬限位上卡了异物。
4. **用手把两指完全拉开**，抵住张开硬限位，在同一对表面之间再次测量，记为 `O_open`。
5. **计算行程：** `stroke = O_open − O_closed`。
6. **重复开合 5 次**，记录每一次读数。取均值作为行程，取离散度作为测量不确定度。
   离散度超过约 0.3 mm 说明机构松动或手推力不一致 —— 先查清原因再继续。

LiteGrip 的预期结果：

| 量 | 预期值 |
| --- | --- |
| `O_open`（完全张开，内侧面到内侧面） | **87.0 mm** |
| 单指行程 | **43.5 mm**（= 行程 / 2） |

单指行程就是 URDF 中 `stroke` 参数所保存的值（写作 `0.0435` m），
因为模型每个手指一个 prismatic 关节；而 87 mm 是 SDK 中 `max_stroke_mm` 的值，
因为 SDK 的位置量覆盖整个开口。

> 若实测值不是 87 mm，**停下来**。SDK 与 URDF 中的每一个常数都由此数推导而来，
> 且 [design-notes.zh-CN.md](design-notes.zh-CN.md#行程限位的推导) 中的几何推导建立在
> mesh 包围盒之上。实测值显著不同，意味着模型与硬件不是同一台设备；
> 先把这件事弄清楚，再标定任何一个。

记录：

```text
O_closed  = ______ mm     （5 次读数：____ ____ ____ ____ ____）
O_open    = ______ mm     （5 次读数：____ ____ ____ ____ ____）
行程      = O_open - O_closed = ______ mm        预期 87.0
单指行程  = 行程 / 2          = ______ mm        预期 43.5
```

## 第 2 步 —— 修正 SDK 的假定行程

SDK 的 mm 刻度来自一个假定行程。该假定是错的，必须在**任何标定运行之前**修掉，
否则你会把一个 1.38 倍的刻度错误烧进标定文件。

有两个地方要改。

**2a. 配置默认值** —— `max_stroke_mm` 被 `calibrate()` 与 `calibrate_manual()` 使用：

```python
# litegrip/models.py, GripperConfig
max_stroke_mm: float = 87.0     # 原为 120.0
```

**2b. `calibrate_guided()` 中的硬编码值** —— 该方法完全忽略配置，用的是字面量：

```python
# litegrip/gripper.py, calibrate_guided()
rad_to_mm = 120.0 / travel      # 原为字面量 120.0
rad_to_mm = self._config.max_stroke_mm / travel     # 修正后
```

确认没有遗漏：

```bash
grep -rn "120\.0" litegrip/gripper.py litegrip/models.py
```

任何出现在位置或换算语境中的 `120.0` 都是缺陷。打印标签（如 `张开(120mm)`）
和文档字符串中的只是外观问题，不影响行为 —— 检查时不要把两者混为一谈。

> **为什么这件事重要。** `rad_to_mm = max_stroke_mm / travel_range`。
> 按假定的 120 mm 和实测的 1.605 rad 范围，出厂标定文件记录的是 `rad_to_mm = 74.8`。
> 按真实的 87 mm，正确值是 `87.0 / 1.605 = 54.21`。
> 在错误刻度下，每次 `goto(60.0)` 实际只开到 43.5 mm，
> 而 `move_at_speed(speed_mm_s=40.0)` 实际只以 29 mm/s 移动。

### 哪些 API 受影响、哪些不受影响

`rad_to_mm` 只存在于面向 mm 的接口上。面向 rad 的调用完全绕过它，
因此刻度错误**不会**让夹爪撞上任何东西 —— 它只是让每一个以毫米计的数都变成错的。

| API | 是否使用 `rad_to_mm` | 刻度偏大 1.38 倍时的后果 |
| --- | --- | --- |
| `get_state().position_mm`、`get_position()` | 是 | 读数偏大 1.38 倍 —— 真实 43.5 mm 的开口会报成 60 mm |
| `goto(position_mm)` | 是 | 目标打得不够：`goto(60)` 只到 43.5 mm |
| `move_at_speed(target_mm, speed_mm_s)` | 是 | 目标与速度同时缩小 1.38 倍 |
| `open()`、`close()`、`goto_rad()`、`move_to()` | **否** —— 这些直接下发 rad | 不受影响，仍能到达真实限位 |
| `close(force_n=...)`、`set_force()` | **否** —— 属于力矩域 | 不受该常数影响；见第 6 步 |
| `grasp()` | **否** —— 堵转检测基于 rad | 不受影响 |

所以刻度错误的标定不会危及机构。它只会静默地污染你读到的每一个位置、
以及你下发的每一条以毫米计的命令 —— 而这更难察觉。

## 第 3 步 —— 标定角度范围

三种方法任选其一。三者都会把夹爪顶到两端硬限位并报出 `travel_range_rad`，
区别在于对硬件自己停住的信任程度。

### 方案 A —— 自动堵转检测（`calibrate`）

朝两端逐步逼近，位置不再变化即停止。无需人工干预，在探测刚度下顶入两端硬限位。

```bash
python examples/calibrate.py --channel can0 --can-id 0x08 --kp 60 --step 0.1
```

从低 `--kp`（60）起步，让两指轻柔地抵住限位。只有在堵转检测过早触发时才提高它。

### 方案 B —— 零重力手动（`calibrate_manual`）

电机失力，由你用手移动两指。**首次标定最安全**，因为夹爪不会自行顶向限位。

```bash
python examples/calibrate_manual.py --channel can0 --mst-id 0x18 --mode manual --duration 30
```

在这 30 秒窗口内，把两指完全推拢、再完全拉开，反复数次。
观察打印出的 `open=` / `close=` 极值，确认两端限位都被采到。

### 方案 C —— 引导式（`calibrate_guided`）

夹爪以低刚度朝各限位逐步逼近，每到达一处等你按 Enter 确认。
当你的这台设备自动堵转检测不可靠时使用。

```bash
python examples/calibrate_manual.py --channel can0 --mst-id 0x18 --mode guided --kp 60
```

> **在完成第 2b 步之前不要跑方案 C。** `calibrate_guided()` 正是那个带硬编码假定的方法；
> 另外两个读配置。

### 读取结果

三种方法都会打印并返回 `CalibrationData`：

```text
闭合极限:   +0.114xxx rad  (0.0 mm)
张开极限:   -1.491xxx rad  (87.0 mm)
行程:        1.605xxx rad
转换系数:   54.2 mm/rad
```

接受之前先做合理性检查：

| 检查项 | 预期 |
| --- | --- |
| `travel_range` | 约 1.6 rad，且为正 |
| 闭合 rad 值 | 为正，接近 `+0.11` |
| 张开 rad 值 | 为负，接近 `-1.49` |
| 张开 rad **小于** 闭合 rad | 必须成立 —— 其符号约定与 mm 相反 |
| 3 次运行的离散度 | 约 0.01 rad 以内。离散度更大说明限位检测不一致 |

**跑 3 次**并比较 `travel_range`。机构是刚性的，它们应当非常接近；
逐次差异大指向的是检测问题，而非真实的机械差异。

## 第 4 步 —— 计算并校验 `rad_to_mm`

若第 2、3 步已完成，该值已经正确：

```text
rad_to_mm = 行程mm / travel_range_rad
          = 87.0 / 1.605
          = 54.21 mm/rad
```

**若你是通过修改已有标定文件而非重跑来修正**，请直接编辑
`~/.litegrip/litegrip_calibration.json`。`load_calibration()` 会从文件读取 `rad_to_mm`，
因此运行时真正起作用的是这个值 —— 一旦载入标定文件，`GripperConfig` 的默认值就不再被参考：

```json
{
  "zero_position_rad": 0.114,
  "max_position_rad": -1.491,
  "travel_range_rad": 1.605,
  "rad_to_mm": 54.21
}
```

每当 `travel_range_rad` 变化，都要重新计算 `rad_to_mm`；绝不要把它跨标定沿用。

### 当前代码库里三个互相打架的值

注意，仓库中目前存在三个不同的「mm 每 rad」，只有最后一个是正确的：

| 来源 | 数值 | 依据 |
| --- | --- | --- |
| `constants.py`，`UnitConversion.RAD_TO_MM` | 105.26 | `120 / 1.14` —— 假定了一个从未实测过的 1.14 rad 范围 |
| `factory_calibration.json`，`rad_to_mm` | 74.8 | `120 / 1.605` —— 范围正确，**行程错误** |
| 本夹爪的正确值 | **54.21** | `87.0 / 1.605` —— 行程与范围均为实测 |

`constants.py` 中的 1.14 rad 既不匹配实测范围，也不匹配出厂文件；
且运行时 `get_state()` 并不使用 `UnitConversion.RAD_TO_MM`。把它当作过时值，
不要拿它做参照。

## 第 5 步 —— 用卡尺验证位置精度

未经实测对照的标定不要采信。

1. 载入标定后，下发一系列位置并等每一个稳定：对 `p` = 0、20、40、60、80、87 执行
   `gripper.goto(p)`。
2. 每个位置用卡尺测量两内侧面之间的开口。
3. 列表记录误差。

| 指令 (mm) | `get_state().position_mm` | 卡尺实测 (mm) | 误差 (mm) |
| --- | --- | --- | --- |
| 0 | ____ | ____ | ____ |
| 20 | ____ | ____ | ____ |
| 40 | ____ | ____ | ____ |
| 60 | ____ | ____ | ____ |
| 80 | ____ | ____ | ____ |
| 87 | ____ | ____ | ____ |

验收标准：最大绝对误差低于 **0.5 mm**，且无系统性趋势。
SDK 标注的重复定位精度是 ±0.03 mm，但那是电机的定位重复性，
不是标定的绝对精度 —— 不要用那个标准去要求绝对值。

**各行存在恒定偏移**，说明 `zero_position_rad` 有偏差 —— 闭合限位被检测在了错误的点上。
**误差随行程成比例增大**（接近 0 处小、接近 87 处大），说明 `rad_to_mm` 有误 ——
最可能是行程假定又溜了回来。回头检查第 2 步。

## 第 6 步 —— 标定夹持力

SDK 用一个固定常数把力矩换算为牛顿：

```python
force_n = torque_nm * UnitConversion.NM_TO_N      # 出厂 NM_TO_N = 10.0
tau_ff  = force_n * UnitConversion.N_TO_NM        # 出厂 N_TO_NM = 0.1
```

`10.0` 是未经核实的标称值。真实比值取决于传动 —— 丝杠导程、减速比、连杆几何 ——
必须实测。

**操作步骤。**

1. 把测力计放在两指之间，居中，并与夹持轴线对齐。
2. 下发一个力矩并读取稳态力。请使用原始的力矩前馈，
   以免同时与位置环较劲：用 `gripper.set_force(force_n=F)` 扫一遍 `F`，
   或直接通过 `send_mit_frame` 下发 `tau`。
3. 记录的是**实测力 vs 下发力矩**，而不是 vs 下发的牛顿值 ——
   下发的牛顿值本身正是由你要求解的那个常数推出来的。
4. 在常用范围内取 5–8 个点，每点至少测 3 次。
5. 拟合 `F_实测 = k * tau`，强制过原点（零力矩必须对应零力）。

   | 下发 `tau` (Nm) | 读数 1 (N) | 读数 2 (N) | 读数 3 (N) | 均值 (N) |
| --- | --- | --- | --- | --- |
   | 0.1 | ____ | ____ | ____ | ____ |
   | 0.2 | ____ | ____ | ____ | ____ |
   | 0.3 | ____ | ____ | ____ | ____ |
   | 0.5 | ____ | ____ | ____ | ____ |
   | 0.8 | ____ | ____ | ____ | ____ |
   | 1.0 | ____ | ____ | ____ | ____ |

6. 在 `UnitConversion` 中令 `NM_TO_N = k`、`N_TO_NM = 1/k`。
7. URDF 用的**最大夹持力**，是「你愿意允许的力矩」处实测到的力，
   而不是电机力矩上限处的力。DM4310 能输出的力矩远超机构所能承受；
   限值应从机构额定值选取，然后记录该限值处的力。

**用砝码验证。** 砝码提供一个不依赖测力计标定的力参考：

1. 用 `gripper.grasp(force_n=F)` 夹住一个已知质量 `m` 的物体。
2. 逐步增大 `F`，直到物体被夹住且不打滑。
3. 最小夹持力应满足 `F >= m * g / (2 * mu)`，其中 `mu` 为指面与物体的摩擦系数。
   在 `mu` 未知时这只能给出一个下界，而非精确值 ——
   它适合抓出量级错误（差 10 倍一眼可见），不适合把常数精确到三位小数。

> **注意温度。** 长时间高力矩堵转会让线圈发热。读取 `state.temperature_coil`，
> 超过约 80 °C 就停下；`0xC` 即线圈过温故障。

## 第 7 步 —— 标定速度，并推导 URDF 的 `velocity`

URDF 的 `velocity` 限值单位是 m/s，且是**单指**速度。
SDK 的 `speed_mm_s` 是整个开口的变化速率。手指的移动速度是开口变化速率的一半：

```text
单指速度 = 开口变化速率 / 2
```

**操作步骤。**

1. 完全张开并等它稳定。
2. 以已知速度走过一段可测距离：
   `gripper.move_at_speed(target_mm=0.0, speed_mm_s=40.0, ...)`。
3. 用秒表计时，或在调用前后打时间戳。
4. 计算实际开口速率：`距离 / 耗时`。
5. 取 3–5 个速度重复，检查实际速率是否跟随指令速率。
   若始终偏低，说明指令速度超出了机构能力 —— 那正是你要找的数。
6. **找真正的上限**：逐步提高速度指令，直到实际速率不再增长。那个平台值就是机械最大开口速率。

   | 指令 (mm/s) | 距离 (mm) | 耗时 (s) | 实测 (mm/s) |
| --- | --- | --- | --- |
   | 20 | ____ | ____ | ____ |
   | 40 | ____ | ____ | ____ |
   | 60 | ____ | ____ | ____ |
   | 85（标称） | ____ | ____ | ____ |

7. 换算为 URDF 值：

```text
URDF velocity = （最大开口速率 mm/s）/ 2 / 1000      [m/s]
```

按标称的 85 mm/s 开口速率，得到 `85 / 2 / 1000 = 0.0425 m/s`，
而占位值是 `0.2` m/s。占位值大约高出 4.7 倍 ——
一个遵守该限值的控制器会下发硬件跟不上的运动指令。

## 第 8 步 —— 摩擦与阻尼（仅仿真）

**除非你在调 Gazebo 或其它物理仿真器，否则跳过本步。**
这两个参数只有仿真器会读；ros2_control 硬件接口会忽略 `<dynamics>`。
它们不影响真机的行为、限值或安全。

两者都在电机**失能**状态下，用测力计手动拉扯手指来测量。

**摩擦**（`<dynamics friction>`，prismatic 关节单位为 N）即突破力：

1. 使电机失能（`gripper.disable()`），确认手指可自由移动。
2. 把测力计挂到一只手指上，沿其行程轴缓慢拉动。
3. 记录手指刚开始移动前的**峰值**力。这就是静摩擦。
4. 在不同起始位置至少重复 5 次；取**中位数**而非均值 ——
   突破力测量有很长的上尾。
5. 以牛顿记录为 `joint_friction`。

**阻尼**（`<dynamics damping>`，单位 N·s/m）是黏性项：

1. 电机保持失能，以若干稳定速度拉动手指，覆盖工作范围。
2. 记录每个速度下的稳态力。
3. 拟合直线：`F = 摩擦 + 阻尼 * v`。**斜率**即阻尼系数。
4. 以 N·s/m 记录为 `joint_damping`。

| 速度 (m/s) | 稳态力 (N) |
| --- | --- |
| 0.01 | ____ |
| 0.02 | ____ |
| 0.04 | ____ |
| 0.08 | ____ |

出厂值（`joint_damping = 0.05`、`joint_friction = 0.02`）是为抑制仿真振荡而选的保守占位值，
并非实测。

## 第 9 步 —— 把实测值写入本包

| xacro 参数 | 来源 | 获取方式 |
| --- | --- | --- |
| `stroke` | 第 1 步 | `行程mm / 2 / 1000` → `0.0435` m |
| `effort` | 第 6 步 | 允许力矩处的最大夹持力 (N) |
| `velocity` | 第 7 步 | `（最大开口速率 mm/s）/ 2 / 1000` |
| `joint_damping` | 第 8 步 | 拟合斜率，N·s/m（**仅仿真**） |
| `joint_friction` | 第 8 步 | 突破力中位数，N（**仅仿真**） |

编辑 [`urdf/litegrip_urdf.urdf.xacro`](../urdf/litegrip_urdf.urdf.xacro) 中的默认值：

```xml
<xacro:arg name="effort"         default="__._"/>    <!-- 第 6 步 -->
<xacro:arg name="velocity"       default="0.____"/>  <!-- 第 7 步 -->
<xacro:arg name="joint_damping"  default="0.____"/>  <!-- 第 8 步，仅仿真 -->
<xacro:arg name="joint_friction" default="0.____"/>  <!-- 第 8 步，仅仿真 -->
```

然后从 [README.zh-CN.md](../README.zh-CN.md#需要标定) 的参数表中删除对应的 ⚠ 占位标记，
并更新 [CHANGELOG.md](../CHANGELOG.md)。

### 关于 `effort` 与 SDK 的 `force_n`

prismatic 关节的 URDF `effort` 是该关节沿其轴向能施加的力 ——
也就是**单只手指**施加到物体上的力。SDK 的 `force_n` 意图上也是夹持力。
因此两者数值应当相等，不需要乘除 2。

这个等价关系值得在第 6 步实测确认，而不是假定：若 SDK 的 `force_n` 被标定为
*分摊到两只手指的总驱动力*而非指-物接触力，则 URDF 取值需要减半。
测力计直接测到的就是指-物接触力，所以请依据实测设置 `effort`，不要依据任何一套约定。

## 安全事项

- **夹伤风险。** 两指会以你标定出的最大夹持力闭合。
  只要电机使能，就让手指远离行程路径，第 3 步期间也不例外。
- **标定会顶入硬限位。** 方案 A 与 C 会刻意让电机在机械限位上堵转。
  请使用仍能可靠检测堵转的最低 `kp`。
- **发热。** 反复堵转测试会让线圈迅速升温。各轮之间读取 `temperature_coil` 并让设备冷却。
- **24 V。** 接线前确认极性与电源能否提供堵转电流。
- **`close()` 并不受标定的力限制。** 实测出的 `NM_TO_N` 只是让 `force_n` 参数*更准确*，
  它并不构成安全限值。请在你自己的应用层对 `force_n` 与 `tau` 做限幅。

## SDK 中已知的不一致

以下问题是通过阅读与本包配套版本的 SDK 发现的。记录在此，
是为了让你能区分「标定问题」与「代码问题」。它们都不能靠标定解决。

| # | 位置 | 问题 | 影响 |
| --- | --- | --- | --- |
| 1 | `models.py`，`GripperConfig.max_stroke_mm` | 取 `120.0`，而真实行程为 87 mm | 一旦烧进 `rad_to_mm`，所有 mm 读数偏大 1.38 倍 |
| 2 | `gripper.py`，`calibrate_guided()` | 硬编码 `120.0 / travel`，忽略配置 | 只改配置并不能修好这个方法 |
| 3 | `gripper.py`，`home()` | 移动到字面量 `POS_CLOSED_RAD = 0.0`，而非 `config.pos_closed_rad` | 标定后（闭合 ≈ `+0.114`），`home()` 会停在张开约 6 mm 处，而不是闭合 |
| 4 | `constants.py`，`POS_OPEN_RAD = 1.14` | 符号与量值都与实测张开限位（≈ `-1.491`）不符 | 当前未被使用 —— 死常量，但具误导性 |
| 5 | `constants.py`，`UnitConversion.RAD_TO_MM = 105.26` | 假定了一个从未实测的 1.14 rad 范围 | 运行时不使用；代码库中流通着三个不同的 mm/rad |
| 6 | `models.py`，`GripperState.aperture_mm` | 文档字符串称「单侧位移；总开口需乘 2」 | 与 `move_at_speed` 的「0=闭合，120=张开」及标定数学相矛盾。数学上把 `max_stroke_mm` 当作**整个**开口；文档字符串是错的 |
| 7 | `constants.py`，`UnitConversion.NM_TO_N = 10.0` | 未经核实的标称值 | 在第 6 步完成前，夹持力指令只是近似 |
| 8 | `gripper.py`，`calibrate()` | 打印 `张开(120mm)` | 仅外观问题；完成第 2a 步后计算值是正确的 |

第 3 项需要特别留意：`home()` 与 `close()` **并不**去往同一个位置，而 `home()` 是异常的那个。
